# ADR 0006: Authentication Strategy — OAuth for Users, Custom Tokens for Agents

## 1. Context and Problem Statement

Harmost has two distinct principals that need to authenticate against the hub:

1. **Users** — humans accessing the system via the React frontend. They need identity, session management, and org scoping.
2. **Agents** — long-running Go processes running on remote machines that open a persistent gRPC stream to the hub. They are non-interactive and must authenticate without human involvement.

These two principals have fundamentally different security models, lifecycles, and threat surfaces. A single auth strategy cannot optimally serve both. The current codebase uses an `x-org-id` header placeholder that must be replaced before the system can be exposed to real users or real agents.

## 2. Considered Options

**User auth:**
* **Option A: GitHub OAuth (primary) + other OAuth providers** — Delegate identity to external providers. GitHub is the primary target audience (developers). Additional providers (Google, GitLab) can be added later via the same abstraction.
* **Option B: Email + password (local auth)** — Full control, but requires password hashing, reset flows, email verification, and brute-force protection. High build cost for a developer-focused product where everyone has a GitHub account.
* **Option C: Magic link (passwordless email)** — Good UX, but requires email infrastructure and introduces email delivery as a dependency.

**Agent auth:**
* **Option A: Custom org-scoped tokens** — Hub generates opaque tokens scoped to an org. Agents present the token on the gRPC stream. Hub validates it, resolves the org, and injects the org context. Tokens can be rotated, revoked, and audited.
* **Option B: mTLS** — Strong cryptographic identity but requires a PKI, certificate distribution, and rotation infrastructure. Operationally complex for the target user (a developer running an agent on a laptop or VM).
* **Option C: Shared secret / API key** — Simpler than mTLS but provides no per-agent identity and no revocation granularity below the org level.

## 3. Decision

**Users:** OAuth 2.0 with GitHub as the primary provider. The hub acts as the OAuth callback handler, exchanges the code for a profile, creates or updates the user row, and issues a signed JWT for subsequent API calls. Additional OAuth providers (Google, GitLab) can be added behind the same interface without changing downstream code.

**Agents:** Custom org-scoped tokens generated by the hub. On pairing, the user generates a token in the UI scoped to their org. The agent is configured with this token and presents it as a gRPC metadata header (`authorization: Bearer <token>`) on every `Connect` call. The hub validates the token, resolves the `org_id`, and injects it into the stream context — replacing the current `x-org-id` placeholder.

**Justification:** Separating the two strategies lets each principal use the mechanism that best fits its nature. OAuth removes the password management burden for users (GitHub login is ubiquitous among developers). Custom tokens for agents keep pairing simple (copy-paste a token) while supporting fine-grained revocation and audit without PKI complexity.

## 4. Consequences

**Positive:**
* No password storage or reset flow required for users.
* Agent tokens can be rotated or revoked per-org without touching user sessions.
* The JWT issued after OAuth can carry `org_id` and `user_id` claims, making the `x-org-id` header placeholder a straight swap.
* Additional OAuth providers require only a new provider config, not architectural changes.
* Agent token validation is a single DB lookup — cheap and auditable.

**Negative / Trade-offs:**
* GitHub OAuth requires registering an OAuth App and managing a `CLIENT_ID` / `CLIENT_SECRET` in config.
* Agents cannot authenticate without a network round-trip to the hub to validate the token (no offline validation unlike JWTs). This is acceptable since agents are always online when connecting.
* JWT expiry and refresh must be handled in the frontend.

### Canonical Token Schema Addition

```sql
agent_tokens (id, org_id, name, token_hash, created_by, created_at, last_used_at, revoked_at)
```

Tokens are stored hashed (bcrypt or SHA-256). The plaintext is shown once at creation time.

---

## 5. AI Directives (System Rules)

* **MUST:** User authentication MUST go through OAuth. Never implement local email/password auth.
* **MUST:** GitHub is the primary OAuth provider. Additional providers MUST be added behind a shared `OAuthProvider` interface, not as parallel code paths.
* **MUST:** Agent authentication MUST use org-scoped tokens presented as `authorization: Bearer <token>` in gRPC metadata. Never use a plain `x-org-id` header in production code paths.
* **MUST:** Agent tokens MUST be stored hashed in the `agent_tokens` table. Never store plaintext tokens.
* **MUST NOT:** Never use the `x-org-id` metadata/header as a trust boundary — it is a development placeholder only. In production, `org_id` must be resolved from a validated JWT (users) or a validated agent token (agents).
* **MUST:** On user signup via OAuth, create a personal org and owner membership in the same transaction as the user row (see ADR 0004).
* **REFERENCE:** See ADR 0004 for the multi-tenancy model and how `org_id` scopes all resources.
